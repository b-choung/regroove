# REGROOVE - 채용 공고 통합 트래커 (Job Application Tracker)

여러 채용 사이트에 흩어진 공고를 한곳에 모아 관리하고, 지원 프로세스를 칸반보드로 추적하는 개인 프로젝트입니다. 다시 리듬을 탄다는 의미를 부여해 REGROOVE라는 이름을 붙였습니다.

## 왜 만들었나

3년차 프론트엔드 개발자로, 2년의 공백 이후 재취업을 준비하면서 사람인·원티드·잡플래닛 등 여러 사이트에 흩어진 채용 공고를 스프레드시트로 관리하다가 한계를 느껴 직접 만들었습니다. 단순한 튜토리얼 프로젝트가 아니라 실제로 구직 활동에 사용하고 있는 도구입니다.

## 핵심 기능

### 1. 공고 등록

- URL을 붙여넣으면 페이지를 파싱해 제목, 회사명, 기술스택, 마감일을 자동으로 추출
- 자동 파싱이 실패하면 수동 입력 폼으로 대체

### 2. 지원 상태 관리 (칸반보드)

- 컬럼: 관심 → 지원 준비 → 지원 완료 → 서류 합격 → 면접 → 결과
- 드래그 앤 드롭으로 카드 상태 이동 (낙관적 업데이트, 실패 시 롤백)
- 카드 클릭 시 상세 정보와 메모(면접 일정, 담당자 연락처 등) 확인
- 카드에서 바로 삭제 (확인 모달을 거치고, 메모는 FK cascade로 함께 삭제)

### 3. 기술스택 매칭

- 본인의 기술스택을 미리 등록
- 공고에서 추출한 기술스택과 비교해 매칭률(%) 표시
- 매칭되지 않는 스택 하이라이트

### 4. 대시보드

- 요약: 전체 공고, 진행 중, 최근 7일 추가, 마감 임박 건수
- 지원 단계 전환: 단계별 누적 건수와 서류 통과율·면접 전환율
- 마감 알림: 마감이 지났거나 일주일 안에 마감하는 공고 (누르면 그 자리에서 상세 모달)
- 상태별 분포: 보드 컬럼에 쌓인 공고 수

## 데이터 모델

```
JobPosting
- id, userId, url, company, title, deadline
- requiredSkills: string[]
- status: enum (interested, applying, applied, document_passed, interview, result)
- source: enum (saramin, wanted, jobplanet, manual)
- rawContent: text (파싱 실패 대비 원본 저장)
- position: double precision (칸반 컬럼 내 정렬 위치)
- createdAt, updatedAt

Note (JobPosting에 종속)
- id, jobPostingId, content, createdAt

UserSkillProfile
- skills: string[]
- experienceYears: number
```

`position`을 정수가 아니라 실수로 둔 이유: 드래그로 카드를 재정렬할 때 이웃 두 카드의 중간값을 넣으면 카드 한 장만 UPDATE 하면 되므로, 컬럼 전체의 순서를 다시 쓰지 않아도 됩니다.

모든 테이블은 RLS로 `auth.uid() = user_id`인 행만 접근할 수 있고, 스키마는 [supabase/migrations/](supabase/migrations/)에 기록합니다.

## API

클라이언트는 Supabase를 직접 호출하지 않고 전부 자체 API Route를 거칩니다. (RLS 위에 서버 검증을 한 겹 더 두고, 3주차 외부 사이트 파싱의 CORS 우회 경로를 같은 자리에 두기 위함)

| 메서드 | 경로                           | 설명                                |
| ------ | ------------------------------ | ----------------------------------- |
| GET    | `/api/job-postings`            | 목록 (position 순)                  |
| POST   | `/api/job-postings`            | 생성 (해당 컬럼 맨 아래에 배치)     |
| GET    | `/api/job-postings/[id]`       | 단건 조회                           |
| PATCH  | `/api/job-postings/[id]`       | 부분 수정 / 상태 이동 (낙관적 잠금) |
| DELETE | `/api/job-postings/[id]`       | 삭제                                |
| GET    | `/api/job-postings/[id]/notes` | 공고의 메모 목록 (최신순)           |
| POST   | `/api/job-postings/[id]/notes` | 메모 추가                           |
| DELETE | `/api/notes/[id]`              | 메모 삭제                           |
| POST   | `/api/parse`                   | 공고 URL 파싱 (폴백 체인)           |
| GET    | `/api/skill-profile`           | 내 스킬 프로필 (없으면 null)        |
| PUT    | `/api/skill-profile`           | 내 스킬 프로필 저장 (upsert)        |

실패 응답은 `{ error: { code, message, fields? } }` 형태로 통일했고, 클라이언트는 HTTP status 대신 `code`(`unauthorized`, `invalid_request`, `not_found`, `conflict`, `duplicate_url`, `internal_error`)로 분기합니다.

### 동시 편집 충돌 (낙관적 잠금)

PATCH에 클라이언트가 마지막으로 본 `expectedUpdatedAt`을 함께 보내면, 서버가 `updated_at`이 일치하는 행만 UPDATE 합니다. 0행이 갱신되면 그 사이 누군가 먼저 수정한 것이므로 409와 **서버의 최신 공고**를 함께 돌려주고, 클라이언트는 그 값으로 캐시를 덮어써 "최신 상태 우선" 정책을 맞춥니다.

## 아키텍처: 카드 이동과 낙관적 업데이트

드래그로 카드를 옮길 때 서버 응답을 기다리면 카드가 손에서 놓은 자리로 잠깐 튀어 보입니다. 그래서 이동은 세 단계로 처리합니다.

```
드롭
  │
  ▼
1. planMove(): 이웃 두 카드의 중간값으로 새 position 계산 (카드 한 장만 UPDATE)
  │
  ▼
2. onMutate: 캐시를 먼저 고쳐 화면을 즉시 반영 + 이전 상태 스냅샷 보관
  │           ├─ 실패 → onError: 스냅샷으로 롤백
  │           └─ 409 충돌 → 서버가 함께 보낸 최신 공고로 맞춤
  ▼
3. onSettled: 목록 무효화 → 서버 순서로 최종 일치
```

드래그 중에는 미리보기를 `DragOverlay`로만 그리고, 실제 이동은 드롭 시점에 한 번 계산합니다. `onDragOver`마다 컬럼 사이로 카드를 옮겨 두는 흔한 구현은 드래그 중 순서를 담을 로컬 미러 상태가 필요해서, 서버 상태(TanStack Query)와 두 갈래로 갈라집니다.

## 아키텍처: 공고 파싱 폴백 체인

사이트마다 마크업 구조가 달라 100% 자동 파싱이 불가능하다는 문제를, 3단계 폴백 구조로 해결했습니다.

```
URL 입력
  │
  ▼
1단계: 구조화 메타데이터 (schema.org JobPosting JSON-LD → OG 메타태그)
  │ 채우지 못한 필드가 남으면
  ▼
2단계: 본문 텍스트를 Claude에 넘겨 빈 필드만 추출
        (구조화 출력으로 스키마 강제, 이미 아는 값은 known으로 전달)
  │ 그래도 남으면
  ▼
3단계: missing 목록을 폼에 표시해 사용자에게 입력 요청
```

**JSON-LD를 OG보다 먼저 보는 이유**: OG에는 제목과 사이트 이름 정도만 있어서 회사명조차 부정확합니다(`og:site_name`은 "원티드"처럼 플랫폼 이름이 옵니다). 회사명·마감일·기술스택이 필드로 들어 있는 건 schema.org `JobPosting`뿐입니다.

**2단계를 "실패했을 때"가 아니라 "부족할 때" 부르는 이유**: OG만 있는 페이지는 제목만 얻고 나머지가 비는데, 그대로 넘기면 자동 추출의 의미가 거의 없습니다. 이미 채운 값은 `known`으로 넘겨 다시 묻지 않고, LLM 응답으로 덮어쓰지도 않습니다(1단계 값이 더 신뢰도가 높습니다).

폴백 순서 자체는 의존성을 주입해 단위 테스트로 고정했습니다. 아키텍처 원칙이라 조용히 깨지면 안 되기 때문입니다.

클라이언트에서 외부 채용 사이트로 직접 요청하면 CORS에 막히므로 Next.js API Route가 서버에서 대신 가져옵니다. 다만 "사용자가 준 URL을 서버가 요청한다"는 건 SSRF 통로이기도 해서, 내부망 주소(localhost·사설망·클라우드 메타데이터)를 막고 리다이렉트를 직접 따라가며 매 홉을 다시 검사합니다.

## 아키텍처: 스킬 매칭

공고의 요구 스택과 내 스택을 비교하는데, 표기가 제각각입니다("React.js", "리액트", "react"). 비교 전에 정규화하고 널리 쓰이는 표기 차이만 별칭으로 흡수합니다.

별칭 표를 무한히 늘리는 대신, 상세 화면에 **겹치는 스택과 없는 스택을 공고 표기 그대로** 나열합니다. 정규화가 잘못 묶었을 때 사용자가 바로 알아볼 수 있어야 하기 때문입니다.

## 아키텍처: 대시보드 통계

통계 전용 API를 두지 않고, 보드가 이미 쓰는 목록 캐시(`useJobPostings`)에서 계산합니다. 개인용 규모(수백 건)에서 집계 쿼리를 얹을 이유가 없고, 보드에서 카드를 옮긴 결과가 대시보드에도 곧바로 반영됩니다. 계산은 순수 함수(`lib/dashboard/stats.ts`)로 빼서 단위 테스트로 고정했습니다.

단계는 **누적**입니다. 면접까지 간 공고는 "지원 완료"도 통과했으므로 상위 단계의 분모에 들어갑니다.

```
지원 완료 이상 = applied + document_passed + interview   ← 서류 통과율의 분모
서류 합격 이상 = document_passed + interview             ← 면접 전환율의 분모
면접           = interview
```

**`result`(결과) 컬럼은 비율 계산에서 제외합니다.** 서류에서 떨어진 공고와 최종 면접까지 가서 떨어진 공고가 같은 `result`에 들어가 있어서, 어느 단계까지 갔는지 알 수 없습니다. 억지로 한쪽에 넣으면 통과율이 실제와 다른 숫자가 되므로, 제외한 건수를 화면에 함께 적었습니다("결과 컬럼의 n건은 … 비율 계산에서 제외했습니다").

정확한 퍼널과 "이번 주 지원 수"에는 상태 전이 이력이 필요합니다(`job_posting_status_events` 같은 테이블에 `from → to`와 시각을 남기는 방식). 지금 데이터 모델로는 만들 수 없는 숫자라서, 대신 계산 가능한 값(`최근 7일 추가` = `createdAt` 기준)으로 바꿨습니다.

## 트러블슈팅

### 1. 한 필드만 수정했는데 나머지 필드가 초기화됐다

수정용 스키마를 `jobPostingInputSchema.partial()`로 만들었는데, Zod의 `.partial()`은 `.default()`를 벗기지 않습니다. 그래서 `{ status: "interview" }`만 담아 PATCH를 보내도 스키마가 `url: null`, `deadline: null`, `requiredSkills: []`, `source: "manual"`을 기본값으로 채워 넣어, 저장해 둔 값이 통째로 날아갔습니다. 매퍼에서 `undefined` 필드를 제외하는 방어 로직이 있었지만 스키마가 이미 값을 채운 뒤라 소용이 없었습니다.

기본값이 없는 필드 정의를 따로 분리해, **생성용 스키마에만 기본값을 얹고 수정용 스키마는 순수 `partial()`로** 만들어 해결했습니다. 회귀를 막는 테스트를 함께 남겼습니다.

### 2. 낙관적 잠금이 항상 실패했다

`expectedUpdatedAt`을 `z.string().datetime()`으로 검증했는데, 이 검증기는 `Z`로 끝나는 표기만 허용합니다. Postgres `timestamptz`는 `2026-08-23T06:00:00.123456+00:00`처럼 오프셋 표기로 직렬화되므로, DB에서 읽은 `updated_at`을 그대로 되돌려보내는 낙관적 잠금 요청이 전부 400으로 거부됐습니다. `z.iso.datetime({ offset: true })`로 교체했습니다.

### 3. Supabase 타입이 통째로 `never`가 됐다

`supabase gen types` 대신 손으로 옮겨 적은 `Database` 타입을 쓰고 있었는데, 모든 `insert`/`update` 호출이 "not assignable to type 'never'"로 실패했습니다. 원인은 두 가지였습니다.

- 테이블 정의에 PostgREST 조인 추론용 `Relationships` 필드가 없었다.
- `Row`를 `interface`로 선언했다. **TypeScript는 interface에 암시적 인덱스 시그니처를 부여하지 않아서** supabase-js가 요구하는 `Record<string, unknown>` 제약을 만족하지 못한다. `type` alias로 바꿔야 통과한다.

둘 중 하나만 어긋나도 스키마 전체가 제약에서 탈락하고, 조건부 타입의 `never` 분기로 떨어져 원인과 동떨어진 에러 메시지가 나옵니다.

### 4. 카드를 계속 같은 자리에 끼워 넣으면 순서가 무너진다

이웃 두 카드의 중간값을 쓰는 방식은 간격이 매번 반으로 줄어듭니다. 1024에서 시작해도 같은 두 카드 사이에 50번쯤 끼워 넣으면 두 position이 double 정밀도상 같은 값이 되고, 그때부터 순서가 무작위가 됩니다. 실사용으로 도달하기 어려운 경계지만 조용히 망가지는 종류라, 간격이 `MIN_POSITION_GAP`보다 좁아지면 그 컬럼 전체에 번호를 다시 매기는 폴백을 넣었습니다. 80번 연속 삽입해도 순서가 유지되는지 테스트로 고정했습니다.

재정렬 요청은 이동한 카드에만 낙관적 잠금(`expectedUpdatedAt`)을 걸고, 함께 번호를 고치는 나머지 카드에는 걸지 않습니다. 위치를 정리하는 후속 작업까지 잠금을 걸면 남이 만진 카드 한 장 때문에 정렬 복구 전체가 막힙니다.

### 5. 카드 클릭이 드래그로 오인됐다

카드 안에 상세 열기 버튼, 삭제 버튼, 원문 링크가 있어서 카드 전체를 드래그 대상으로 만들면 클릭이 삼켜집니다. 전용 손잡이에만 드래그 리스너를 붙이고, `PointerSensor`에 8px 활성화 거리를 둬서 이중으로 막았습니다. 손잡이는 버튼이라 `KeyboardSensor`로 키보드 이동도 됩니다. dnd-kit 기본 안내 문구는 영어라 "관심 컬럼에 놓았습니다" 식의 한국어 안내로 교체했습니다.

### 6. 낙관적 업데이트가 진행 중인 refetch에 덮어써졌다

`onMutate`에서 캐시를 고쳐도, 그 시점에 이미 날아간 목록 refetch가 늦게 도착하면 이전 순서로 되돌아갑니다. `onMutate` 첫 줄에서 `cancelQueries`로 진행 중인 요청을 먼저 끊어 해결했습니다.

### 7. API 요청이 JSON 대신 HTML을 받아왔다

세션이 없는 요청을 `/login`으로 리다이렉트하는 미들웨어(Next.js 16의 `proxy.ts`)가 `/api/*`까지 함께 리다이렉트하고 있었습니다. `fetch`는 리다이렉트를 따라가 로그인 **페이지 HTML**을 200으로 받아오고, 클라이언트는 그걸 JSON으로 파싱하다 엉뚱한 에러를 던졌습니다. API 경로는 리다이렉트 대신 401 JSON을 반환하도록 분기해, 클라이언트가 세션 만료를 코드로 구분할 수 있게 했습니다.

### 8. 본문 텍스트를 뽑자 JSON-LD가 사라졌다

Cheerio로 본문 텍스트를 만들 때 `script`, `style`을 지웠는데, JSON-LD도 `<script type="application/ld+json">`이라 함께 지워졌습니다. 텍스트 추출을 메타데이터 파싱보다 먼저 호출한 탓에 1단계가 통째로 실패하고 매번 2단계(LLM)로 내려갔습니다 — 결과는 맞게 나오니 조용히 비용만 나가는 종류의 버그였습니다. `body`를 복제한 뒤 지우도록 고쳐, 호출 순서에 의존하지 않게 만들었습니다.

### 9. URL을 불러오면 사용자가 입력해 둔 값이 사라졌다

공고 폼이 자체 state를 들고 있어서, 파싱 결과를 채우려는 부모가 "사용자가 지금 입력한 값"을 알 수 없었습니다. 부모가 가진 오래된 초기값에 파싱 결과를 합쳐 폼을 다시 mount 했기 때문에, 마감일을 먼저 입력하고 URL을 불러오면 그 값이 조용히 지워졌습니다. 폼을 controlled로 바꿔 값의 주인을 부모로 올리고, 회귀 테스트를 남겼습니다.

### 10. 특수문자를 지우자 C++와 C#이 같은 스킬이 됐다

스킬 정규화에서 특수문자를 전부 제거했더니 "C++", "C#", "C"가 모두 `c`로 접혀 서로 매칭됐습니다. 공백·점·하이픈·밑줄만 지우고 `+`와 `#`은 남기도록 좁혔습니다. 같은 종류의 함정이라 버전 번호 제거(`Vue3` → `Vue`)도 넣지 않았습니다 — `S3`, `EC2`가 `S`, `EC`로 망가집니다.

### 11. 마감 D-day와 타임존 (설계 단계에서 걸러낸 함정)

마감일은 시각이 없는 날짜(`2026-09-01`)입니다. 남은 일수를 `new Date(deadline) - Date.now()`로 재면 `Date`가 날짜 문자열을 **UTC 자정**으로 파싱하므로, 한국에서 오전 9시 전에는 "오늘 마감"이 "1일 지남"으로 나옵니다. 반대로 로컬 타임존으로 파싱하면 DST가 있는 지역에서 하루가 23·25시간이 되어 또 어긋납니다.

그래서 "오늘"을 정하는 책임만 `todayInSeoul()`에 모으고, 비교는 두 날짜를 UTC 자정으로 맞춰 일수로만 계산하는 순수 함수로 분리했습니다(`lib/job-postings/deadline.ts`). 경계(UTC 15:30 = KST 다음 날 00:30, D-7)는 테스트로 고정했습니다.

### 12. 분모가 0인 비율은 0%가 아니다

지원한 공고가 없으면 서류 통과율이 `0/0`입니다. 여기서 `0%`를 찍으면 "아직 계산할 수 없다"와 "지원했지만 전부 떨어졌다"가 같은 화면으로 보입니다. 비율은 `number | null`로 두고 `null`은 `—`로 그립니다. 3주차 스킬 매칭에서 "요구 스택이 없는 공고의 매칭률"을 `null`로 둔 것과 같은 규칙입니다.

## 배포 (Vercel)

1. GitHub 저장소를 Vercel에 임포트합니다. Next.js 프리셋 그대로 두면 빌드 설정을 만질 필요가 없습니다.
2. Project Settings > Environment Variables에 `.env.example`과 같은 이름으로 세 값을 넣습니다.
3. Supabase 대시보드 > Authentication > URL Configuration에 배포 주소를 등록합니다.
   - Site URL: `https://<도메인>`
   - Redirect URLs: `https://<도메인>/auth/callback` (프리뷰 배포까지 쓰려면 `https://<프로젝트>-*.vercel.app/auth/callback`도 함께)
4. 새 Supabase 프로젝트를 쓴다면 `supabase/migrations/`의 SQL을 SQL Editor에서 실행합니다.

**배포했는데 로그인 링크가 localhost로 온다면** 3번을 건너뛴 것입니다. Supabase는 매직링크의 `emailRedirectTo`를 허용 목록과 대조해서, 목록에 없으면 에러 대신 조용히 Site URL로 바꿉니다.

`ANTHROPIC_API_KEY`는 없어도 배포가 됩니다. 파싱 체인 2단계(LLM 추출)만 꺼지고 메타데이터 → 수동 입력으로 넘어갑니다.

푸시 전 로컬 확인:

```bash
npm test && npm run typecheck && npm run lint && npm run build
```
